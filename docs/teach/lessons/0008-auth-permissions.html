本课只学一件事

Lesson 0007 讲了 DB 层的 tenantIsolation。本课回答：请求是怎么带上 tenant 上下文的？登录失败 vs 权限不足有什么区别？二开写 route 该挂哪些中间件？

LibreChat 的访问控制是分层叠加的 — 不是「一个 if admin」搞定。

四层门禁（由外到内）

HTTP 请求 │ ├─ ① 鉴权 Auth requireJwtAuth / optionalJwtAuth → 401 Unauthorized │ └─ tenantContextMiddleware（有 user 时写入 ALS tenantId） │ ├─ ② 功能 RBAC generateCheckAccess → 403 Forbidden │ PermissionTypes × Permissions（Role 文档里的布尔矩阵） │ ├─ ③ 系统 Capability requireCapability → 403 Forbidden │ SystemCapabilities（admin 管理面，principals 解析） │ └─ ④ 资源级 ACL canAccessResource / PermissionService → 403/404 「这条 prompt / agent 能不能被这个用户读写？」

本课聚焦 ①②③；资源级 ACL 在改 prompts/agents 共享时按需深入。

① 鉴权：requireJwtAuth vs optionalJwtAuth

中间件无 token有 token典型 route
requireJwtAuth401req.user + tenant ALS/api/convos、/api/skills
optionalJwtAuth继续，req.user 为空同上/api/banner、/api/config

样本：Banner（Lesson 0006）— 登录与否展示不同公告：

// api/server/routes/banner.js router.get('/', optionalJwtAuth, async (req, res) => { res.send(await getBanner(req.user)); // user 可能为 undefined });

getBanner(user) 在 methods 里：无 user 时只查 isPublic: true。

requireJwtAuth 成功后自动链 tenant：

passport.authenticate('jwt') → req.user = user → tenantContextMiddleware(req, res, next) → tenantStorage.run({ tenantId, userId, requestId }) → 下游 Mongoose 查询被 tenantIsolation 插件 scope

来源：requireJwtAuth.js · tenant.ts

与 Lesson 0007 的衔接：applyTenantIsolation 在 Model 层注册；tenantContextMiddleware 在 请求层写入 ALS。两者配对，缺一则多租户查询要么漏 filter、要么 strict 模式 403。

② 功能 RBAC：PermissionTypes × Permissions

共享枚举在 packages/data-provider/src/permissions.ts — 前后端同一套契约。

PermissionTypes.SKILLS + Permissions.USE → 能否打开 Skills 功能 PermissionTypes.AGENTS + Permissions.CREATE → 能否新建 Agent PermissionTypes.MCP_SERVERS + Permissions.SHARE → 能否共享 MCP 配置

后端：generateCheckAccess 查 Role 文档（getRoleByName(user.role)）：

// api/server/routes/skills.js const checkSkillAccess = generateCheckAccess({ permissionType: PermissionTypes.SKILLS, permissions: [Permissions.USE], getRoleByName, }); router.get('/', requireJwtAuth, checkSkillAccess, handler);

拒绝时返回 403 + Forbidden: Insufficient permissions（不是 401）。

前端镜像：同一矩阵，避免 UI 显示用户用不了的功能：

// client/src/hooks/Roles/useHasAccess.ts const hasAccess = roles[user.role]?.permissions?.[permissionType]?.[permission] === true;

二开规则：加了 generateCheckAccess 的 route，UI 侧用相同 PermissionTypes + Permissions 做 useHasAccess gating。

③ 系统 Capability（管理面）

RBAC 管「普通用户能用什么功能」；Capability 管「谁能进管理后台、改角色、读审计」等系统级操作。

// api/server/routes/admin/roles.js const requireAdminAccess = requireCapability(SystemCapabilities.ACCESS_ADMIN); const requireManageRoles = requireCapability(SystemCapabilities.MANAGE_ROLES); router.put('/:roleName', requireJwtAuth, requireAdminAccess, requireManageRoles, ...);

requireCapability 由 generateCapabilityCheck 工厂创建，注入 getUserPrincipals / hasCapabilityForPrincipals（~/models）。

来源：capabilities.ts · roles/capabilities.js

动手：Trace 一条受保护 route

在 IDE 里打开 api/server/routes/skills.js，从文件顶部往下找 middleware 栈：

1
router.use(requireJwtAuth) — 全 router 必须登录
2
checkSkillAccess / checkSkillCreate — RBAC gate
3
个别路由还有 canAccessSkillResource — 资源级 ACL（第 ④ 层）

对比 routes/banner.js：只有 optionalJwtAuth，无 RBAC — 因为公告是公开/半公开读。
