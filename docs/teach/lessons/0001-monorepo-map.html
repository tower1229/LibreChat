LibreChat Monorepo 地图

搞清「代码该写在哪」——二开的第一块地基。

Mission: 深度二开 · 宏观架构

你要学会的一件事

看到任意二开需求时，能在 10 秒内判断：改动应落在哪个 workspace， 以及数据/类型如何在包之间流动。不需要记住每个文件——先建立地图。

全景：六个关键 workspace

LibreChat 是 npm workspaces monorepo。根目录 package.json 声明：

"workspaces": ["api", "client", "packages/*"]

来源：package.json · 详见 CLAUDE.md

Workspace路径角色
client /client React SPA。页面、组件、React Query hooks（client/src/data-provider/）。
data-provider /packages/data-provider 前后端共享：类型、API 路径、请求函数。二开的「契约层」。
client (pkg) /packages/client 前端共享 UI 工具（非主应用）。
api (pkg) /packages/api 新后端逻辑写这里（TypeScript）。业务、服务、中间件。
data-schemas /packages/data-schemas MongoDB models/schemas，DB 相关共享逻辑。
api (legacy) /api Express 入口 + JS 路由。尽量薄，调用 packages/api。

依赖方向（背下来）

client ↓ 依赖 packages/data-provider ←→ packages/client ↑ 被两端使用 api (legacy /api) → 调用 packages/api → 使用 packages/data-schemas → 使用 packages/data-provider
二开黄金法则（来自 CLAUDE.md）：
新后端 → packages/api（TS）
共享类型/endpoint → packages/data-provider
DB schema → packages/data-schemas
/api 只加薄路由，不堆业务逻辑

用前端经验类比

如果你熟悉「前端 monorepo + 共享 types 包」，可以这样映射：

你可能熟悉的LibreChat 对应
App 壳 + 页面client/
@org/api-types + fetch 封装packages/data-provider
UI 组件库packages/client
BFF / Server（你要新学的）packages/api + /api 入口
ORM / 数据模型packages/data-schemas（Mongoose）

动手：在仓库里验证

打开以下文件各扫一眼（不用读完），感受「地图上的地标」：

  1. packages/data-provider/src/api-endpoints.ts — endpoint 常量
  2. packages/data-provider/src/data-service.ts — 前端怎么调 API
  3. api/server/index.js — Express 启动（注意 import @librechat/api）
  4. client/src/routes/index.tsx — 前端路由

路径相对于仓库根目录。详见 docs/teach/RESOURCES.md。

✓ 检查理解（3 题）

1. 你要给 LibreChat 加一个新的 REST endpoint，业务逻辑应该主要写在哪？

2. 前后端都要用到的 TypeScript 类型和 API 路径常量，应该放在哪？

3. MongoDB 的 schema / model 定义主要在哪个 workspace？
